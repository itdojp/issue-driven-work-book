### 良い例

- 背景: 決済画面で 500 が発生
- 目的: 決済が完了し、エラー率が通常水準に戻る
- スコープ: 決済 API の入力バリデーションとエラーハンドリング
- 非スコープ: 決済画面のデザイン刷新、決済プロバイダ変更
- 再現手順: 1) カートに追加 2) 決済 3) 500
- 期待: 決済が完了し完了画面へ遷移
- 実: 500 + エラーページ
- 環境: Chrome 122 / macOS 14
- 公開用要約: マスキング済みの再現手順で決済 API が 500 を返し、直近1時間のエラー率が 3.5% まで上昇
- 公開可否: マスキング後に公開可
- マスキング確認: 顧客名、決済情報、token、request-id を除去済み（確認者=Issue Owner、確認日=YYYY-MM-DD）
- 公開用ログ: `status=500 error=validation_failed` の必要最小限の抜粋
- 公開用スクリーンショット: 顧客情報を除去したエラー画面
- 非公開証跡の保管先/参照方法: 制限付き記録 `EVD-EXAMPLE-001`。アクセスが必要な Reviewer は Issue Owner へ申請
- 根拠種別: 再現ログ + アプリケーションログ
- 未確定点: 特定ブラウザのみか全利用者影響かは追加確認
- 影響: 直近1時間の決済エラー率が 0.2%→3.5%（例）、暫定回避策はリトライ案内
- 責任分界: 判断=PM、実行=開発、確認=CS（例）
- 受け入れ条件: Given=決済情報が不正、When=決済、Then=決済は成立せず「原因が分かるエラー」が返る/エラー率が基準値内
- 確認方法: 単体テスト、決済 API のエラーログ、監視ダッシュボード
